# WKB

Договор (contract) за структуриран изход, който всеки агент/модел спазва —
така че записите могат да се рутират, валидират и сравняват машинно, без да
чакат човек да ги парсне на око.

Този repo е референтната дефиниция. Другите repos (напр.
[`euintelhub-lang/ecosystem`](https://github.com/euintelhub-lang/ecosystem))
имплементират WKB за собствения си контекст и линкват насам.

## Защо съществува

Design by contract: изход без schema се губи или се тълкува свободно всеки
път наново. Изход по WKB е или валиден, или FAILED — без сива зона. Един
по-раншен тест показа разликата директно: 100% успеваемост с наложена
schema, 0% без нея.

## Основен принцип: Prefix-decodable order

Полетата в WKB запис са подредени така, че **routing може да стане преди
целият payload да пристигне** — консуматорът чете префикса и вече знае
накъде да насочи записа, без да чака останалото.

Ред: `type → status → regime → meta`

- `type` — какъв запис е (класификация още преди да знаеш резултата)
- `status` — как е минало (SUCCESS / PARTIAL / FAILED и т.н.)
- `regime` — в какъв контекст/режим е създаден
- `meta` — всичко останало — свободно, не влияе на routing

Ако добавяш ново поле, питай първо: "трябва ли routing да го знае преди
останалото?" Ако да — то отива преди `meta`, не след.

## Формат

YAML front-matter + Markdown body:
- Front-matter = структурирани данни (машината чете, валидира се срещу schema)
- Body = свободен текст (човекът чете)

## WKB-in / WKB-out — лек протокол между LLM-и

По подразбиране WKB описва само изхода (**WKB-out**) — какво връща
агент/модел. Щом повече от един модел участва в едно решение (напр.
триангулация — няколко модела отговарят на един и същ вход и се
сравняват), трябва и входът да е стандартизиран, иначе моделите получават
несравним context и сравнението на изходите им е безсмислено.

- **WKB-out** — какво връща модел. Носи `status`, защото описва завършен
  резултат.
- **WKB-in** — какво влиза в модел, преди да отговори. Няма `status`
  (резултатът още не съществува), но носи `request_id`, за да могат
  отговорите на няколко модела да се съберат обратно към един и същ вход.
  Версионира се отделно от WKB-out — промяна в единия договор не значи
  автоматична промяна в другия.

И двата спазват същия prefix-decodable принцип и същата FAILED/WARNING
таблица по-горе.

Това прави WKB **mediated** протокол между LLM-и — общ формат за вход и
изход, координиран през оркестратор, не директна LLM-към-LLM връзка.
Достатъчно е за сравнение и routing между модели; не покрива handshake
или модел, викащ модел в реално време — това е отделна, по-тежка задача,
ако някога потрябва.

## Версиониране

Всеки запис носи `schema_version`. Промяна в schema-та:
- **minor** (напр. 1.0 → 1.1) — ново optional поле с default стойност,
  старите записи остават валидни без миграция.
- **major** (напр. 1.x → 2.0) — breaking change, изисква migration script и
  замразяване на старата версия в история, преди да се допусне нов запис.

Стар запис се валидира срещу **своята** `schema_version`, никога срещу
текущата.

## Валидация — какво е FAILED, какво е само warning

| Проблем | Резултат |
|---|---|
| Unparseable YAML front-matter | FAILED |
| Липсващо required поле | FAILED |
| Невалидна enum стойност | FAILED |
| Липсващ `schema_version` | FAILED |
| `schema_version`, за която няма замразена schema | FAILED |
| Непознато допълнително поле | WARNING (не FAIL — може да е от по-нова версия) |

## Референтна имплементация

`euintelhub-lang/ecosystem`:
- `contracts/agent-output.schema.yaml` — WKB-out schema за агентски изход
  (required/optional полета, enum-и, версия).
- `contracts/wkb-input.schema.yaml` — WKB-in schema за входа, който
  `triangulation-orchestrator` конструира преди fan-out към няколко модела.
- `contracts/schema-versioning.yaml` — правилата за major/minor по-горе,
  приложени.
- `contracts/schema-history/` — замразени версии (за двата договора
  поотделно), за да останат старите записи четими.
- `.github/workflows/validate-schema.yaml` + `scripts/validate_logs.py` +
  `scripts/validate_agents.py` — CI, който проверява горната таблица при
  всеки push/PR.

Ако имплементираш WKB в нов repo, линкни го тук в списъка.
